## BLOCKER

**B-1 — `supabase/migrations/20260831115000_employee_avatars.sql:19` (also `:25`, `:37`): the migration targets a `storage.policies` table that does not exist, so the whole transaction aborts and `avatar_url` is never added.**
Supabase's `storage` schema contains `buckets`, `objects`, `migrations`,
`prefixes` and the `s3_multipart_*` tables — there is no `policies` table;
storage access rules are ordinary RLS policies on `storage.objects`. The
`delete from storage.policies …` on line 19 raises
`relation "storage.policies" does not exist`, which rolls back the enclosing
`begin;…commit;` — including the `alter table public.employees add column if
not exists avatar_url` on line 7 and the bucket insert on line 11. Deploying
this packet therefore leaves the avatar route writing to a non-existent bucket
and every avatar read broken. No other migration in this repo touches the
`storage` schema, so there is no in-repo precedent proving otherwise.
*Fix:* keep the `storage.buckets` upsert, drop lines 18–45, and express the
rules as RLS policies on `storage.objects` guarded for idempotency, e.g.
`drop policy if exists "Avatar public read" on storage.objects; create policy
"Avatar public read" on storage.objects for select using (bucket_id =
'avatars');` plus an `for insert to authenticated with check (bucket_id =
'avatars')` counterpart — then re-run the migration against a scratch database
before it goes anywhere near production.

## MAJOR

**M-1 — `app/mitarbeiter/profil/page.tsx:43` (used at `:58`): the "Direkte Führung" card can never render; the local type cast hides a field the query never fetches.**
`getCurrentEmployee()` selects
`id,auth_user_id,vorname,nachname,email,rolle,department_id,location_id,tenant_id`
(`lib/auth/getCurrentEmployee.ts:23`) — `reports_to_employee_id` is not among
them. Line 43 casts the result to
`typeof employee & { reports_to_employee_id: string | null }`, so line 58's
`currentEmployee.reports_to_employee_id` is always `undefined`, the manager
query is short-circuited to `Promise.resolve({ data: null })`, and every
employee always sees "Noch keine Führungskraft hinterlegt." (`:116`). This is
exactly the "Typen-Fix" the report celebrates — the cast silenced `tsc` over a
runtime hole. It also makes the report's HOW TO VERIFY step 3
("Verantwortungsbereiche und Führungskraft sichtbar") untrue, and it fails
packet requirement 1 (who reports to whom at a glance) on the mobile surface.
`app/mitarbeiter/page.tsx:123` shows the correct pattern.
*Fix:* add `reports_to_employee_id` to the `profile` select on line 48, read it
from `profile`, and delete the cast on line 43.

**M-2 — `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:286`: the AssignmentWizard fires two mutations fire-and-forget, so a failed Führungs-Zuordnung is silently swallowed and reported as success.**
`steps.forEach((step, index) => window.setTimeout(step, index * 120))` launches
`move_employee` and `assign_responsibility` as two unsequenced
`startTransition` fetches 120 ms apart. `mutation()` begins with `setError('')`
(`:121`), so when the `move_employee` call fails (hierarchy cycle rejected by
`move_employee_in_organization`, 403 on location scope, network error) its
error banner is wiped by the second call, which then sets
"Hauptverantwortung zugewiesen." The owner sees a green confirmation for a
change that did not happen. The 120 ms gap also gives no ordering guarantee.
*Fix:* replace the timeout fan-out with one sequential async handler that awaits
step 1 and only runs step 2 when it succeeded, and leave the first error visible.

**M-3 — `app/mitarbeiter/profil/page.tsx:122`: raw database enum shown in the staff UI.**
`Status: {profile.status}` renders `in_probe`, `in_training` or `aktiv` verbatim
on a screen every employee opens; line 121 does the same for `employment_type`
with nothing but a `charAt(0).toUpperCase()`. Master rule 3 is binding —
"German owner-friendly UI … NEVER show JSON or technical data in normal UI" —
and the codebase already carries German labels for these exact values
(`app/(admin)/applications/page.tsx:20` maps `in_probe` → "In Probearbeit").
*Fix:* add a `statusLabel`/`employmentLabel` map next to the existing
`roleLabel` helper at `app/mitarbeiter/profil/page.tsx:31` and render through it.
