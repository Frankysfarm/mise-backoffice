## BLOCKER

**B-1 — `supabase/migrations/20260831115000_employee_avatars.sql:19` (also `:25`, `:37`): the migration targets a `storage.policies` table that does not exist, so the whole transaction aborts and `avatar_url` is never added.**
Supabase's `storage` schema contains `buckets`, `objects`, `migrations`,
`prefixes` and the `s3_multipart_*` tables — there is no `policies` table;
storage access rules are ordinary RLS policies on `storage.objects`. The
`delete from storage.policies …` on line 19 raises
`relation "storage.policies" does not exist`, which rolls back the enclosing
`begin;…commit;` — including the `alter table public.employees add column if
not exists avatar_url` on line 7 and the bucket insert on line 11. Deploying
this packet therefore leaves the avatar route writing to a non-existent bucket
and every avatar read broken. No other migration in this repo touches the
`storage` schema, so there is no in-repo precedent proving otherwise.
*Fix:* keep the `storage.buckets` upsert, drop lines 18–45, and express the
rules as RLS policies on `storage.objects` guarded for idempotency, e.g.
`drop policy if exists "Avatar public read" on storage.objects; create policy
"Avatar public read" on storage.objects for select using (bucket_id =
'avatars');` plus an `for insert to authenticated with check (bucket_id =
'avatars')` counterpart — then re-run the migration against a scratch database
before it goes anywhere near production.

## MAJOR

**M-1 — `app/mitarbeiter/profil/page.tsx:43` (used at `:58`): the "Direkte Führung" card can never render; the local type cast hides a field the query never fetches.**
`getCurrentEmployee()` selects

`typeof employee & { reports_to_employee_id: string | null }`, so line 58's

query is short-circuited to `Promise.resolve({ data: null })`, and every

packet requirement 1 (who reports to whom at a glance) on the mobile surface.
`app/mitarbeiter/page.tsx:123` shows the correct pattern.
*Fix:* add `reports_to_employee_id` to the `profile` select on line 48, read it
from `profile`, and delete the cast on line 43.

**M-2 — `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:286`: the AssignmentWizard fires two mutations fire-and-forget, so a failed Führungs-Zuordnung is silently swallowed and reported as success.**

`move_employee` and `assign_responsibility` as two unsequenced
`startTransition` fetches 120 ms apart. `mutation()` begins with `setError('')`

change that did not happen. The 120 ms gap also gives no ordering guarantee.

entirely ordinary "Diese Zuordnung würde einen Hierarchie-Kreis erzeugen." (409,
`app/api/operations/responsibility/route.ts:173`) produced by a normal
drag-and-drop — now raises an `unhandledrejection` in the browser on top of the
correct error banner. In `next dev` that pops the error overlay over the UI the
owner is using; in production it is console noise and spurious reports in any
error tracker. Before the fix the same failures were silent.
*Fix:* make the fire-and-forget sites explicit — `void mutation(...).catch(() => {})`
— or have `mutation()` resolve to a `boolean` and let the wizard branch on it
instead of on a rejection.

**n-10 — MINOR — `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:123`.**
The `fetch` inside the promise executor is not wrapped in `try/catch`, so if
`fetch` itself rejects (offline, DNS, aborted navigation — the normal failure mode
on the mobile surface this wizard exists for) neither `resolve()` nor `reject()`
is ever called. The wizard's `await mutation(...)` then hangs forever: no error
banner, no `setAssignmentWizardOpen(false)`, and with React 18.3.1 the async
scope function passed to `startTransition` swallows the rejection. The user sees
a save button that did nothing.
*Fix:* wrap the body in `try { … } catch (cause) { setError('Änderung fehlgeschlagen.'); reject(cause); }`.

**n-11 — MINOR — `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:284–286`.**
The wizard's guard is `payload.reportsToEmployeeId !== undefined && payload.employeeId`,
and `AssignmentWizard`'s save always supplies `reportsToEmployeeId` (an id or
`null`), so `move_employee` fires on every save — even when the user only wanted
to set a Bereich and left the Führung untouched. `move_employee_in_organization`
updates the row unconditionally
(`supabase/migrations/20260829204500_responsibility_scope_and_organization_audit.sql`,
`perform set_config('app.audit_employee_id',…)` then `update public.employees …`),
so each no-op save writes an organization-audit row recording a reassignment that
did not change anything, and the owner is told "Zuordnung aktualisiert." for a
non-change. `handleDragEnd` (`:154`) already has exactly the guard that is missing
here: `byEmployee.get(employeeId)?.reports_to_employee_id === parentId → return`.
*Fix:* skip the `move_employee` step when the selected value equals the person's
current `reports_to_employee_id`.

**n-12 — MINOR — `supabase/migrations/20260831115000_employee_avatars.sql:27–32`.**
The `"Avatar authenticated write"` policy grants **every authenticated user of the
Supabase project** `insert` on `storage.objects` for the whole `avatars` bucket,
with no tenant or path scoping. Nothing in the app uses that capability: the only
writer is `app/api/employees/avatar/route.ts:55`, which goes through
`createServiceClient()` and bypasses RLS entirely (`components/avatar-uploader.tsx:48`
posts to the route, it never touches storage directly). Net effect is a capability
the product does not need: any logged-in employee can push arbitrary
JPEG/PNG/WebP objects up to 2 MB into a **public** bucket at any path, i.e. use
the customer's Supabase project as an anonymous image host, with no cleanup path
(cf. N-4). In fairness this shape was prescribed verbatim by my own B-1 fix note
in round 1, so it is my finding to correct, not an implementer error.
*Fix:* either drop the write policy entirely (the service-role route needs no
policy), or scope it with `with check (bucket_id = 'avatars' and (storage.foldername(name))[1] = (select e.tenant_id::text from public.employees e where e.auth_user_id = auth.uid()))`.

**N-7 — NOTE — `supabase/migrations/20260831115000_employee_avatars.sql:19–23`.**
`"Avatar public read"` has no `to` clause, so it applies to `PUBLIC`, including
`anon`. Because the bucket is already `public = true`, image delivery goes through
the unauthenticated public object endpoint and does not need this policy at all;
what the policy additionally enables is the storage **list** API for anonymous
callers, which exposes the object names — i.e. `<tenant_id>/<employee_id>-xxxx.jpg`
— and lets an unauthenticated visitor enumerate tenant and employee UUIDs. Every
server route re-checks tenant scope, so this is disclosure of identifiers rather
than of data, but the policy buys nothing in exchange. Same origin as n-12 (my
round-1 fix text). Worth revisiting together with n-12 in a follow-up migration.

**N-8 — NOTE — `docs/agents/reports/2026-08-31-k-b.md`, "Typen" section.**
