## BLOCKER

### BLOCKER 1 — `revoke all on table training_modules from anon,authenticated` breaks two existing, untouched features
`supabase/migrations/20260831100944_application_assessments_training_onboarding.sql:439`

The revoke removes `select`/`insert` for the `authenticated` role, but two code
paths still reach `training_modules` as `authenticated`, and neither was migrated
in this packet:

- `app/(admin)/training/ai-create/page.tsx:114` — a `'use client'` component that
  inserts a generated module through the **browser** client
  (`createClient` from `@/lib/supabase/client`). After this migration the insert
  returns `permission denied for table training_modules`, surfaced to the owner
  via `toastError('Speichern fehlgeschlagen', error.message)`. The entire
  "AI Training erstellen" flow — reachable from the Schulungen page header — dies.
- `app/(admin)/employees/[id]/page.tsx:35` — a server component using the
  **user-scoped** client (`createClient` from `@/lib/supabase/server`, line 24)
  with the embedded resource
  `training_progress.select('*,module:training_modules(titel,kategorie)')`.
  PostgREST requires `select` on the embedded table for the requesting role, so
  the Schulungen block on every employee detail page starts erroring.

Fix: keep `grant select on public.training_modules to authenticated` (RLS still
scopes rows) and port `ai-create`'s save to the new `/api/training/modules` route
inside this packet, exactly as `app/(admin)/training/new/page.tsx` was ported.

### BLOCKER 2 — `process_overdue_trainings` collides with the pre-existing `operational_tasks_source_uidx` and 500s the whole daily cron
`supabase/migrations/20260831100944_application_assessments_training_onboarding.sql:686-688`

The insert writes `source_type='training_overdue'`, `source_id=progress.id::text`,
but the `on conflict` target names only the new partial index
`operational_tasks_training_progress_uq` (`… where training_progress_id is not
null and status<>'storniert'`). `operational_tasks` already carries a **full**
unique index `operational_tasks_source_uidx on (tenant_id, source_type, source_id)`
(`supabase/migrations/20260828174510_unified_operations_and_table_ordering.sql:335`)
with no partial predicate.

Reproducible failure: a manager cancels the auto-created overdue-training task
(`status='storniert'` is reachable via `app/api/operations/responsibility/route.ts:53`).
The next cron tick no longer matches the partial index, falls through to a plain
insert, and violates `operational_tasks_source_uidx` → `unique_violation` →
`process_overdue_trainings` raises → `app/api/cron/operational-escalations/route.ts:36`
returns `{ok:false}` / HTTP 500. The daily Tagesklarheit run then reports failure
on every subsequent tick with no self-healing path.

Fix: drop the `status<>'storniert'` predicate from the partial index (or add
`on conflict (tenant_id,source_type,source_id) do nothing` as well) so both unique
indexes are covered by a conflict clause.

## MAJOR

### MAJOR 3 — Managers can read, rewrite and delete another location's Bewerbungstest
`app/(neo)/neo/app/tests/page.tsx:11`, `app/api/application-assessments/[id]/route.ts:9`, `:23-28`, migration `:520`

All three paths scope by `tenant_id` only. `save_application_assessment_template`
checks the manager's location against the **incoming** `p_location_id`
(migration `:487`), never against the location of the template being edited
(`where t.id=p_id and t.tenant_id=p_tenant_id`, line 520). A `manager` at
location A therefore sees location B's tests in the list, can open them, and can
save them — which forcibly relocates the template to location A — or `DELETE`
them outright with no location predicate at all. This is the tenant/location
scope invariant the reference `save_shift_operational_template` pattern exists to
enforce.

Fix: add `and (t.location_id is null or t.location_id = v_actor.location_id)` to
the edit lookup for `rolle='manager'`, and filter the list/GET/DELETE by
`actor.location_id` for managers.

### MAJOR 4 — Raw Postgres/English error text is rendered in owner- and applicant-facing UI
`app/api/application-assessments/route.ts:29`, `app/api/application-assessments/public/[token]/route.ts:33`, `:35`, `app/api/applications/[id]/review/route.ts:106`

Every one of these returns `error.message` from the RPC verbatim, and the UI
prints it: `app/(neo)/neo/app/tests/assessment-manager.tsx:21`, `:24`, `:25`
(`setMessage(data.error)` → red box) and `app/bewerbungstest/[token]/test.tsx:8`
(`setError(result.error)` → shown to the applicant). A German-speaking owner sees
`assessment does not match candidate department`, `question 3 is invalid`,
`manager is outside assessment location`; an applicant whose link expired mid-test
sees `assessment session is not active`. This directly contradicts owner order §1
("Die Bedienung darf keine technischen Kenntnisse erfordern"), §7 ("Technische
Daten … dürfen an keiner Stelle in der normalen Benutzeroberfläche erscheinen")
and coordination rule 6.

Fix: map the known RPC exception strings to German sentences in the route and
return a single generic German fallback for anything unmapped.

### MAJOR 5 — Migration grants `insert/update/delete` on `training_progress` to `authenticated` with no policy in this repo
`supabase/migrations/20260831100944_application_assessments_training_onboarding.sql:441`

Every read/write path this packet adds goes through `createServiceClient()`
(`app/mitarbeiter/schulungen/page.tsx:8`, `app/api/training/my/[id]/route.ts:9`,
`app/api/training/assign/route.ts:12`). The only remaining `authenticated` writer
is the browser insert at `app/(admin)/training/ai-create/page.tsx:135`. Granting
`insert,update,delete` to `authenticated` means the new quiz gate is only as
strong as a `training_progress` RLS policy that lives outside this repository —
if the fusion policy allows self-row updates, an employee can set
`status='bestanden', abgeschlossen=true` straight from the browser console and
skip every Wissenstest, and `training_attempts` (service-role only) will show no
attempt.

Fix: narrow to `grant select on public.training_progress to authenticated` and
route the `ai-create` assignment through `/api/training/assign`; if the write
grant must stay, add the self/manager policy explicitly in this migration so it
is reviewable.

### MAJOR 6 — Non-atomic quiz-key replacement can leave a module that everyone auto-passes at 100 %
`app/api/training/modules/route.ts:25-29`

Line 25 deletes all `training_module_targets` and `training_quiz_keys` for the
module; line 28 re-inserts them; line 29 reports the error. There is no
transaction. If the key insert fails (constraint, network, the
`points between 1 and 100` check), the module row is already saved and its answer
keys are gone. `app/api/training/my/[id]/route.ts:12` then computes
`max === 0 → score = 100 → passed = true` and writes `status='bestanden'` for
every employee who opens it. The same window exists for any employee submitting
between the DELETE and the INSERT.

Fix: move save+targets+keys into one `security definer` RPC (as the assessment
side already does), and treat "module has quiz blocks but zero keys" as
not-scoreable rather than as a 100 % pass.

### MAJOR 7 — A test targeted at more than one Bereich or Stelle can never be assigned from the Bewerbung
`app/(admin)/applications/[id]/page.tsx:102`

The filter is
`!(template.targets ?? []).some(t => t.target_type === 'department' && t.department_id !== application.department_id)`.
With targets `[Küche, Service]` and a candidate in Küche, the `Service` row makes
`.some(...)` true and the template is dropped. Identical bug on the position
branch. So exactly the case owner order §1 asks for — "unterschiedliche Tests für
verschiedene Stellen und Bereiche" — is the case the picker hides. It also
disagrees with `assign_application_assessment` (migration `:744-755`), which uses
"if any department target exists, one must match".

Fix: `const deps = targets.filter(t => t.target_type === 'department'); deps.length === 0 || deps.some(t => t.department_id === application.department_id)` and the same for positions.

### MAJOR 8 — Training description is rendered as raw HTML to every employee
`app/mitarbeiter/schulungen/[id]/runner.tsx:8`

`dangerouslySetInnerHTML={{ __html: progress.module.beschreibung }}` — but the

### MAJOR 10 — `process_overdue_trainings` violates `operational_tasks.location_id NOT NULL` for employees without a location
`supabase/migrations/20260831100944_application_assessments_training_onboarding.sql:686`

### BLOCKER 2 — NOT-FIXED; the fix makes the failure unconditional

`migration :733` now reads `on conflict(tenant_id,source_type,source_id) do nothing`
with the partial-index predicate dropped from
`operational_tasks_training_progress_uq` (`:418-420`). But the arbiter it targets,
`operational_tasks_source_uidx`, **is itself partial**
(`20260828174510_…sql:335-337`, `where source_type is not null and source_id is not null`).
Postgres cannot infer a partial index unless the `ON CONFLICT` clause carries an
`index_predicate` that implies it. The repo's own reference does exactly that
(`20260830113000_shift_linked_operational_tasks.sql:525-526`:
`on conflict(tenant_id,source_type,source_id) where source_type is not null and source_id is not null`);
the new function omits it.

Reproduced against the production schema snapshot with this migration applied,
on an **empty** `training_progress` (no overdue rows, no cancelled task needed):

```
select public.process_overdue_trainings();
ERROR:  there is no unique or exclusion constraint matching the ON CONFLICT specification
```

and the isolated control, which succeeds:

```
… on conflict(tenant_id,source_type,source_id)
  where source_type is not null and source_id is not null do nothing;   -- INSERT 0 0
```

Impact is strictly worse than before the fix: previously the daily run broke only
after a manager cancelled an auto-created task; now
`app/api/cron/operational-escalations/route.ts` returns `{ok:false}`/HTTP 500 on
**every** tick from the first deploy, because the statement fails at plan time
regardless of row count. The dry-run's `exit 0` does not cover this — plpgsql
bodies are not planned at `CREATE FUNCTION` time.

Fix: append `where source_type is not null and source_id is not null` to the
conflict target, and keep the `training_progress_id` index non-partial as it now is.

### NEW MAJOR 24 — the `training_progress` de-duplication silently deletes passed/certified rows
`supabase/migrations/20260831100944_…sql:382-384`

```sql
delete from public.training_progress duplicate
using public.training_progress keeper
where duplicate.id>keeper.id and duplicate.employee_id=keeper.employee_id and duplicate.module_id=keeper.module_id;
```

The survivor is chosen by lowest `id` (a random uuid), not by state. The realistic
duplicate shape in production is exactly the one MINOR 14 described — the legacy
`ai-create` bulk assignment re-inserting `(employee_id, module_id)` — so the pair is
typically one stale `offen` row and one later row that may be `bestanden` with
`testergebnis`, `passed_at` and `abgeschlossen=true`. Whichever uuid sorts lower
wins, so a completed mandatory-training record can be destroyed. `training_attempts`
rows for the deleted progress cascade away with it (FK `on delete cascade`,
verified on the snapshot). The delete emits no `raise notice`, writes no
`audit_log`, and is irreversible after `commit`.

Fix: order the de-duplication by state, e.g. keep
`(abgeschlossen desc, passed_at desc nulls last, fortschritt_prozent desc, id)`
per `(employee_id, module_id)`, and `raise notice` the number of rows removed so
the deploy log records it.

### NEW BLOCKER 31 — `digest()` is unresolvable under `set search_path=public,pg_temp`; test creation and test completion both fail on the production schema
`supabase/migrations/20260831100944_…sql:11`, `:531` + `:615`, `:700` + `:718`

`create extension if not exists pgcrypto` (`:11`) is a no-op on the production
database, because pgcrypto is already installed there — in the **`extensions`**
schema, not `public` (verified on the snapshot: `pgcrypto → extensions`, alongside
`pg_net`, `pgjwt`, `uuid-ossp`). Two of the new RPCs call `digest()` unqualified while
declaring `set search_path=public,pg_temp`, which excludes `extensions`:

- `save_application_assessment_template` (`:531` / `:615`, the version `checksum`)
- `complete_application_assessment` (`:700` / `:718`, `input_checksum` and
  `result_checksum` on the `assessment_results` insert)

Both raise at runtime. Reproduced against the production schema snapshot with this
migration applied:

```
select public.save_application_assessment_template(… );
  ERROR:  function digest(bytea, unknown) does not exist
  CONTEXT: … line 72 at SQL statement   (insert into assessment_template_versions)

assign → session uuid      start → t      submit → (100.00,QUIZ)

  ERROR:  function digest(text, unknown) does not exist
  CONTEXT: … line 17 at SQL statement    (insert into assessment_results)

-- isolated control on the same database:
set search_path=public,pg_temp;             select digest('x','sha256');  -- ERROR
set search_path=public,extensions,pg_temp;  select digest('x','sha256');  -- ok
```

Impact, on the first deploy, with no precondition:

- No owner, backoffice user or manager can create **or edit any Bewerbungstest**.
  `app/api/application-assessments/route.ts:32` returns 400 and
  `assessment-manager.tsx:24` shows "Der Bewerbungstest konnte nicht verarbeitet
  werden. Bitte versuche es erneut." — the entire owner-facing entry point of this
  packet is dead, and the message gives no clue why.
- An applicant can open the link, answer every question and submit — `assign`,
  `start` and `submit` all work, so the responses are stored — and then the final
  `complete` call fails. `app/bewerbungstest/[token]/test.tsx` shows the generic
  German error, the session stays `IN_PROGRESS`, no `assessment_results` row is ever
  written, and the Bewerbung never shows a result. Retrying re-runs the same failure.
- This also blanks the "hire → automatic onboarding trainings" chain in practice,
  because it can only be reached through a completed test's `next_stage` action.

The DDL dry-run's exit 0 does not cover this: plpgsql bodies are not resolved at
`CREATE FUNCTION` time, and on a database where pgcrypto does *not* already exist the
`create extension` at `:11` installs it into `public`, so the same code passes locally
and fails in production. This is the second time in this packet that a runtime-only
plpgsql failure survived a green dry-run.

Fix: schema-qualify both calls (`extensions.digest(...)`), or add `extensions` to the
`search_path` of the two functions, matching wherever the rest of the platform resolves
pgcrypto. `gen_random_uuid()` is fine — it comes from `pg_catalog` on PG13+, and I

### NEW MAJOR 32 — a manager silently relocates a tenant-wide Bewerbungstest to their own location, removing it from every other location
`supabase/migrations/20260831100944_…sql:554`, `:592`; `app/(neo)/neo/app/tests/assessment-manager.tsx:27`

The MINOR 17 fix makes `v_location_id` unconditionally the manager's own location and
writes it on the update path (`:592 location_id=v_location_id`), while the MAJOR 3 edit
guard (`:588`) deliberately lets managers open templates with `t.location_id is null`.
So any manager who opens a tenant-wide test — created by the owner with "Alle
Standorte" — and presses "Test speichern" converts it into their own location's test.
Other locations lose it from `app/(neo)/neo/app/tests/page.tsx:11`, from the
assignment picker (`app/(admin)/applications/[id]/page.tsx:103` filters on
`!template.location_id || template.location_id === application.location_id`), and from
`assign_application_assessment` (`:807-809`). The manager cannot undo it — they cannot
set the location back to `null`. There is no confirmation, no error and no audit hint:
`audit_log` records only `assessment_updated` with `version_id`/`active`, not the
location change.

Reproduced against the production schema snapshot (with a search_path-patched copy of
the function in the throwaway database, to get past BLOCKER 31):

```
owner creates "Globaler Test" with p_location_id = null   → location_id = NULL
manager at Standort A saves the same template, choosing "Alle Standorte"
                                                          → location_id = Standort A
```

Round 1 could reach this only if the manager happened to pick their own location from
the dropdown; round 2 makes it the outcome of every manager save, including a save
where the manager explicitly chose "Alle Standorte". The same override also means a
manager who deliberately picks "Standort B" gets a Standort-A test with no feedback.

Fix: for `rolle='manager'`, reject (with a German message) any `p_location_id` that is
neither `null`-meaning-unchanged nor the manager's own location, and never widen or
narrow an existing template's location on a manager save — or hide the location select
for managers entirely, as MINOR 17 originally proposed.

### NEW MINOR 33 — department targets are validated against the location that was discarded
`supabase/migrations/20260831100944_…sql:673`

The target loop still validates against **`p_location_id`**
(`and (p_location_id is null or d.location_id=p_location_id)`) while the template row
is stored with `v_location_id` (`:592`). For a manager the two now always disagree, so
the check is performed against a scope the template does not have. Reproduced in the
same run as MAJOR 32: a manager at Standort A saved a template that ended up at
Standort A carrying a department target belonging to Standort B, with no error. The
result is not a scope leak — `assign_application_assessment` blocks the candidate on
the template location — but it is a silently accepted configuration that can never
match any candidate, and the owner has no way to see why the test is never offered.
Fix: use `v_location_id` in the department check.
