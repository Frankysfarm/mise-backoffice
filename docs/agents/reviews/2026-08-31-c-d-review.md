## BLOCKER

### B1 — The Konflikt-Engine and the proposal scoring are dead code

`lib/scheduling/planner.ts:47` (also `:34`, `:83`, `:98`)

`evaluateScheduleConflicts`, `scoreProposal`, `missingTemplateInstances`,
`templateInstanceKey` and `affectedEmployees` are imported by exactly one file:
`tests/scheduling/planner.test.ts:2`. No page, component, API route or RPC
calls them. The owner therefore never sees Doppelbelegung, fehlende
Qualifikation, Ruhezeit < 11 h, Urlaub, Krankheit, Vertragsstunden or
Minderjährigen-Nachtarbeit anywhere in the product, and no shift is flagged as
`unbesetzt` / `Konflikt` / `Unterbesetzung`. The packet's "Konflikt-Engine" and
required end-state item 6 are unimplemented in the shipped surface; the 10
green unit tests assert behaviour that never runs. This also creates a second,
divergent scoring model next to the SQL engine (`scoreProposal` weights
140/110/35/+20 vs. the SQL 120/100/35/+20), i.e. the parallel system that
coordination rule 5 forbids.
*Fix:* wire `evaluateScheduleConflicts` into the week board (`week-view.tsx`)
and the suggestion list so every proposed/manual assignment renders its German
conflicts, and delete `scoreProposal` in favour of the SQL engine's score.

### B2 — The migration breaks the already-shipped Wochen-Dienstplan-Assistent

`supabase/migrations/20260831130000_schedule_planning_loop.sql:115-122`,
consumed by `app/api/operations/schedule-suggestions/route.ts:94`

`generate_weekly_shift_assignment_suggestions` is renamed to `_v1` and replaced
by a wrapper that raises `availability deadline is not set` whenever no
`schedule_weeks` row with a deadline exists for that tenant/location/week.
`schedule_weeks` rows are created **only** by `apply_schedule_template`
(`:87`), so every week planned manually — i.e. every week that exists today —
makes the existing "Vorschläge berechnen" button fail. The error text contains
neither `not allowed`/`outside` nor `available`, so `scheduleFailure()`
(`schedule-suggestions/route.ts:117-124`) turns it into the generic 400
"Wochenvorschläge konnten nicht verarbeitet werden." — the owner gets no hint
that a deadline is missing. A working production feature regresses to broken.
*Fix:* fall back to the `_v1` behaviour when no planning round exists instead of
raising, and surface a specific German message when a deadline is required.

### B3 — Availability answers do not influence who is proposed

`supabase/migrations/20260831130000_schedule_planning_loop.sql:124-135` vs.
`supabase/migrations/20260830154500_daily_clarity_automation.sql:527-550`

`_v1` selects exactly one candidate per shift (`order by … limit 1`) and inserts
one suggestion per shift *before* the wrapper runs. The wrapper can therefore
only re-score and re-label a decision that is already made: `kann`/`moechte`
adds 20/45 points to the row that was chosen without knowing about them, and
`kann_nicht` (`:131`) merely flips that row to `obsolete`, leaving the shift
with **no** proposal at all rather than the next best candidate. On the next
"Vorschläge berechnen", `_v1` re-suggests the same person (it never reads
`shift_availability_responses`) and the wrapper obsoletes them again — a
permanent loop in which a shift somebody declined can never receive an
alternative. Packet requirement 5 and owner point 5 ("Die KI erstellt anhand
der Verfügbarkeiten … einen Dienstplan") are not met.
*Fix:* extend the `_v1` candidate query itself with a
`shift_availability_responses` join (exclude `kann_nicht`, boost
`moechte`/`kann`) instead of post-processing its output.

### B4 — The migration is not re-runnable and can corrupt the suggestion engine on retry

`supabase/migrations/20260831130000_schedule_planning_loop.sql:46-55`, `:115`, `:137`

Coordination rule 1 requires idempotent additive migrations following the
`save_shift_operational_template` pattern; the reference migration
`20260830154500` issues `drop policy if exists` before every `create policy`
(`:336-337`). This file contains **zero** `drop policy if exists` for its ten
`create policy` statements, uses `create function
public.record_published_schedule_change()` without `or replace` (`:137`), and —
worst — `alter function public.generate_weekly_shift_assignment_suggestions(…)
rename to …_v1` (`:115`). On any re-apply (`supabase db reset`, a retried push,
a partial failure after `commit`) the rename now targets the **wrapper**, so
either the statement fails with "function already exists" or, if the `_v1`
object were dropped first, the wrapper would call itself recursively. A
migration that cannot be safely retried must not go to production.
*Fix:* add `drop policy if exists` before each policy, `create or replace` the
trigger function, and guard the rename with
`if not exists (select 1 from pg_proc where proname='generate_weekly_shift_assignment_suggestions_v1') then … end if;`.

## MAJOR

### M1 — A planning week can only be opened from a template

`app/(admin)/schedule/planning-controls.tsx:26-27`,
`supabase/migrations/20260831130000_schedule_planning_loop.sql:87`

Packet step 1 says the owner opens the week "from template **or manually**".
`schedule_weeks` is only ever inserted by `apply_schedule_template`, and
"Verfügbarkeit anfragen" / "Dienstplan veröffentlichen" are both disabled while
`initialStatus` is falsy. An owner who builds the week by hand can set no
deadline, request no availability, and publish nothing.
*Fix:* add an `openWeek` action that upserts `schedule_weeks` with a deadline
independently of any template.

### M2 — Editing a week template destroys idempotency of "Vorlage anwenden"

`supabase/migrations/20260831130000_schedule_planning_loop.sql:72`, `:91`

`update` deletes all `schedule_template_slots` and re-inserts them, minting new
slot UUIDs. The instance key is `slot.id:week_start:n`, so re-applying an edited
template to a week that already has its shifts creates a **full duplicate set**
of open shifts — exactly the "re-applying does not duplicate" requirement the
packet calls out, and the route still reports `N offene Schichten erstellt`.
*Fix:* update slots by stable id (or key on
`template_id:weekday:start_time:position:n`) instead of delete-and-recreate.

### M3 — "Geändert seit Veröffentlichung" is never visible to employees

`supabase/migrations/20260831130000_schedule_planning_loop.sql:139-147`;
no reader anywhere in `app/`

`schedule_publication_changes` rows are written but the table is not selected by
a single page or route (`grep` over `app/`, `lib/`: only the migration).
Employees receive a generic "Dienstplan geändert" notification with no
indication of *which* shift changed or how; the packet's step 10 ("employees can
see 'geändert seit Veröffentlichung'") is not delivered.
*Fix:* read the employee's `schedule_publication_changes` on `/mitarbeiter` and
render a "Geändert" badge with the German summary on the affected shift.

### M4 — The owner cannot see any availability response or application

`app/api/scheduling/planner/route.ts:31`; `app/mitarbeiter/page.tsx:163`

`shift_availability_responses` is written by the employee and read back only by
that same employee's page. Nothing in `/schedule` shows who answered
kann / möchte / kann nicht, and "möchte" is documented as a concrete
Bewerbung but never reaches the owner. The RLS policy `shift_availability_own_read`
(`migration:54`) deliberately excludes managers, so the data is not reachable
from the manager UI either. Packet steps 3 and 6 are unmet.
*Fix:* add a manager read policy plus an availability column in the week board
(or the suggestion list) showing the responses per shift.

### M5 — The employee's availability tap fails silently, with a misleading reason

`app/mitarbeiter/availability-loop.tsx:11`;
`app/api/scheduling/planner/route.ts:30`

`if (response.ok) setStates(...)` — every failure path is swallowed: the button
simply does nothing and the employee has no idea whether the answer was saved.
Compounding it, the open-shift list shows every `offen_fuer_bewerbung` shift in
the next 60 days regardless of whether a planning round exists, and any shift
without a `schedule_weeks` row returns `Die Eintragungsfrist ist abgelaufen.`
although the round was never opened. That is a wrong statement to the employee.
*Fix:* toast the server message on failure, and distinguish "Planungsrunde noch
nicht geöffnet" from "Frist abgelaufen".

### M6 — A template can be applied to an already published week without any change record

`supabase/migrations/20260831130000_schedule_planning_loop.sql:79-96`

`apply_schedule_template` never checks `schedule_weeks.status`. Applying a
template to a published week inserts new shifts; the change trigger
(`:151`) fires only `after update of …`, so no `schedule_publication_changes`
row and no notification is produced. A published, binding plan silently grows
new shifts.
*Fix:* raise a German-mapped error when `status='published'`, or record a
`published`-week change row per inserted shift.

## Summary

The data model, the RLS/service-role split and the German owner-facing copy are
mostly sound, and the report is honest about what was and was not executed. But
the packet's two defining deliverables are not actually wired into the product:
the conflict engine exists only as tested-but-unused TypeScript (B1), and the
availability loop does not reach the assignment engine (B3). On top of that the
migration regresses the already-shipped weekly assistant (B2) and cannot be
safely re-applied (B4). Blockers remain, so this packet is not approved.
