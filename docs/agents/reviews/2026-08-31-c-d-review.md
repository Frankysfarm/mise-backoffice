## BLOCKER

### B1 — The Konflikt-Engine and the proposal scoring are dead code

`lib/scheduling/planner.ts:47` (also `:34`, `:83`, `:98`)

`evaluateScheduleConflicts`, `scoreProposal`, `missingTemplateInstances`,
`templateInstanceKey` and `affectedEmployees` are imported by exactly one file:
`tests/scheduling/planner.test.ts:2`. No page, component, API route or RPC
calls them. The owner therefore never sees Doppelbelegung, fehlende
Qualifikation, Ruhezeit < 11 h, Urlaub, Krankheit, Vertragsstunden or
Minderjährigen-Nachtarbeit anywhere in the product, and no shift is flagged as
`unbesetzt` / `Konflikt` / `Unterbesetzung`. The packet's "Konflikt-Engine" and
required end-state item 6 are unimplemented in the shipped surface; the 10
green unit tests assert behaviour that never runs. This also creates a second,
divergent scoring model next to the SQL engine (`scoreProposal` weights
140/110/35/+20 vs. the SQL 120/100/35/+20), i.e. the parallel system that
coordination rule 5 forbids.
*Fix:* wire `evaluateScheduleConflicts` into the week board (`week-view.tsx`)
and the suggestion list so every proposed/manual assignment renders its German
conflicts, and delete `scoreProposal` in favour of the SQL engine's score.

### B2 — The migration breaks the already-shipped Wochen-Dienstplan-Assistent

`supabase/migrations/20260831130000_schedule_planning_loop.sql:115-122`,
consumed by `app/api/operations/schedule-suggestions/route.ts:94`

`generate_weekly_shift_assignment_suggestions` is renamed to `_v1` and replaced
by a wrapper that raises `availability deadline is not set` whenever no
`schedule_weeks` row with a deadline exists for that tenant/location/week.
`schedule_weeks` rows are created **only** by `apply_schedule_template`
(`:87`), so every week planned manually — i.e. every week that exists today —
makes the existing "Vorschläge berechnen" button fail. The error text contains
neither `not allowed`/`outside` nor `available`, so `scheduleFailure()`
(`schedule-suggestions/route.ts:117-124`) turns it into the generic 400
"Wochenvorschläge konnten nicht verarbeitet werden." — the owner gets no hint
that a deadline is missing. A working production feature regresses to broken.
*Fix:* fall back to the `_v1` behaviour when no planning round exists instead of
raising, and surface a specific German message when a deadline is required.

### B3 — Availability answers do not influence who is proposed

`supabase/migrations/20260831130000_schedule_planning_loop.sql:124-135` vs.
`supabase/migrations/20260830154500_daily_clarity_automation.sql:527-550`

`_v1` selects exactly one candidate per shift (`order by … limit 1`) and inserts
one suggestion per shift *before* the wrapper runs. The wrapper can therefore
only re-score and re-label a decision that is already made: `kann`/`moechte`
adds 20/45 points to the row that was chosen without knowing about them, and
`kann_nicht` (`:131`) merely flips that row to `obsolete`, leaving the shift
with **no** proposal at all rather than the next best candidate. On the next
"Vorschläge berechnen", `_v1` re-suggests the same person (it never reads
`shift_availability_responses`) and the wrapper obsoletes them again — a
permanent loop in which a shift somebody declined can never receive an
alternative. Packet requirement 5 and owner point 5 ("Die KI erstellt anhand
der Verfügbarkeiten … einen Dienstplan") are not met.
*Fix:* extend the `_v1` candidate query itself with a
`shift_availability_responses` join (exclude `kann_nicht`, boost
`moechte`/`kann`) instead of post-processing its output.

### B4 — The migration is not re-runnable and can corrupt the suggestion engine on retry

`supabase/migrations/20260831130000_schedule_planning_loop.sql:46-55`, `:115`, `:137`

Coordination rule 1 requires idempotent additive migrations following the
`save_shift_operational_template` pattern; the reference migration
`20260830154500` issues `drop policy if exists` before every `create policy`
(`:336-337`). This file contains **zero** `drop policy if exists` for its ten
`create policy` statements, uses `create function
public.record_published_schedule_change()` without `or replace` (`:137`), and —
worst — `alter function public.generate_weekly_shift_assignment_suggestions(…)
rename to …_v1` (`:115`). On any re-apply (`supabase db reset`, a retried push,
a partial failure after `commit`) the rename now targets the **wrapper**, so
either the statement fails with "function already exists" or, if the `_v1`
object were dropped first, the wrapper would call itself recursively. A
migration that cannot be safely retried must not go to production.
*Fix:* add `drop policy if exists` before each policy, `create or replace` the
trigger function, and guard the rename with
`if not exists (select 1 from pg_proc where proname='generate_weekly_shift_assignment_suggestions_v1') then … end if;`.

## NEW findings

### R1 — BLOCKER: “Dienstplan veröffentlichen” can never succeed

`supabase/migrations/20260831130000_schedule_planning_loop.sql:139`

`publish_schedule_week` inserts `notifications.typ = 'dienstplan'`, but `notifications.typ` is the
enum `public.notification_type`, whose only values in the production snapshot are
`dringend, erfolg, info, warnung`. *(empirically verified)*:

```
ERROR:  invalid input value for enum notification_type: "dienstplan"
CONTEXT: PL/pgSQL function publish_schedule_week(uuid,uuid,uuid,date) line 12
```

The insert is inside the RPC's transaction, so the whole publish aborts: the week never reaches
`status='published'`, no `schedule_publication_changes` row is written, no mail is queued, and the
route returns the generic 400 “Dienstplan-Aktion konnte nicht ausgeführt werden.”
(`planner/route.ts:80`). The draft → published boundary — the packet's central deliverable and the
gate that N1/M3/M6 all hang off — is inoperable. The two `notifications` inserts added by this
branch are the only ones in the entire `supabase/migrations` tree; the shipped application code uses
valid values (`typ: 'warnung'`). This is a defect *missed in round 0*, not one introduced by the
fixes — it is already present in `f42e9a8`.
*Fix:* use a valid `notification_type` (`info`) or add the new labels to the enum in this migration.

Every reassignment, time change, drag-and-drop, edit-dialog save and

merely block the new feature — it breaks the **already-shipped** week board for any published week,
and it is the reason M3's badge can never light up. Severity is higher than R1 because the failure is
in a trigger on the shared `shifts` table and so hits pre-existing surfaces that know nothing about
this packet.
*Fix:* as R1; and add a DB test that publishes a week and then edits a shift in it.

### R3 — MAJOR: “Verfügbarkeit anfragen” reports success while notifying nobody

`app/api/scheduling/planner/route.ts:63-64`, `:67`

The reminder rows use `typ: 'dienstplan_verfuegbarkeit'` — again not a `notification_type` value
*(empirically verified: the same enum error)*. Unlike R1/R2 this insert's error is **discarded**:
`if (rows.length) await service.from('notifications').insert(rows);` has no error check, and the
route then returns `{ ok: true, notified: rows.length }`. The owner is told “Erinnerungen
eingeplant” and that N people were notified; in reality zero in-app notifications exist. The mail
rows still queue, so the failure is invisible on both sides. Reporting a delivery that did not happen
is exactly the honesty rule the packet is built around.
*Fix:* use a valid enum value **and** check the insert error before reporting a count.

### R4 — BLOCKER: the new engine proposes one person for every seat of a multi-person slot

`supabase/migrations/20260831130000_schedule_planning_loop.sql:161-179`

`_v1`'s candidate query dropped two properties that `_core` has: the exclusion of employees who
already hold a `draft` suggestion for an **overlapping** shift
(`20260830154500:518-524`), and the inclusion of already-suggested hours in `assigned_hours`
(`20260830154500:470-477`). `_v1` counts only `public.shifts.employee_id` (`:170-171`), which
suggestions never set — only `confirm_…` does. Nothing therefore changes between iterations of the
per-shift loop, and the deterministic `order by final_score desc, assigned_hours, id` returns the
identical top candidate every time.

*(empirically verified)* — one Monday 08:00–16:00 slot with `headcount: 3`, four eligible employees:

```
NEW public engine → 40000000-…-0001 ×3   (three overlapping shifts, same person)
_core (shipped)   → …0001, …0002, …0003  (one each)
```

Applying a week template with `headcount > 1` and letting the assistant fill it is the packet's
headline scenario; it now yields an impossible plan in which only one of the N seats is fillable.
Confirming the second proposal hits `suggested employee is now double-booked`
(`20260830154500:645`), which the UI shows as “Der Vorschlag ist nicht mehr aktuell.” The board also
cannot flag it: both shifts still have `employee_id is null`, so `evaluateScheduleConflicts` sees no
`doppelbelegung`. The B3 fix traded a real regression for the one it repaired.
*Fix:* port `_core`'s anti-overlap guard and draft-hours accumulation into `_v1`'s candidate query,
or add the availability join to `_core` instead of re-implementing selection beside it.

### R5 — MAJOR: recurring `employee_availability` (`gesperrt`) is ignored, and the reason text denies it

`supabase/migrations/20260831130000_schedule_planning_loop.sql:161-179` (no `employee_availability`
reference anywhere in the file) vs. `20260830154500:502-509`

`_v1` overwrites `_core`'s suggestion for every open shift, but never reads `employee_availability`,
so the recurring weekly availability model — the one the employee maintains — no longer influences
who is proposed. *(empirically verified)*: with employees …0001/…0002/…0003 all holding
`weekday=0, 07:00–17:00, typ='gesperrt'` and only …0004 free,

```
_core (shipped)   → …0004        (correct: the only unblocked person)
NEW public engine → …0001 ×3     (all three blocked people ranked ahead)
```

and the proposal is labelled **“Keine konkrete Sperre eingetragen”** (`migration:183`) for a person
who has an explicit Sperre. That is a false statement shown to the owner in the German reason line.
Owner point 5 (“Die KI erstellt anhand der Verfügbarkeiten … einen Dienstplan”) is met only for the
new per-shift responses, not for the availability data that already exists.
*Fix:* carry `_core`'s `employee_availability` blocked-window predicate into `_v1`, and derive the
reason text from what was actually checked.

### R6 — MINOR: department responsibilities are no longer time-scoped

`migration:175` vs. `20260830154500:481-492`

`_v1`'s responsibility check drops the `responsibility_assignment_active_at(valid_from, valid_until,
weekday_scope, shift_start, shift_end, …)` call, so an expired assignment, or one scoped to other
weekdays or other shift times, now qualifies a candidate.
*Fix:* re-add the scoping call.

### R7 — MINOR: `_core` is executed and then entirely discarded

`migration:157`

`_v1` calls `generate_weekly_shift_assignment_suggestions_core(...)` and then re-selects a candidate
for **every** open shift in the week, upserting over `_core`'s row (`:184`). No `_core` output
survives. The “preserve the proven deterministic assistant instead of creating a parallel engine”
comment at `:145` is therefore nominal: the proven filters are bypassed (R4, R5, R6) while their cost
is still paid on every run. This is the structural cause of the three findings above.
*Fix:* either extend `_core` in place, or stop calling it and own the full filter set explicitly.

### R8 — MINOR: a soft conflict now masks a hard ArbZG error on the week board

`app/(admin)/schedule/week-view.tsx:285`

`const severity = conflicts.some(c => c.severity === 'blocker') ? 'error' : conflicts.length ? 'warn' : highestSeverity(warnings);`

When a shift has any non-blocker conflict (e.g. `bereich`) *and* an ArbZG `error` (e.g.
`arbzg_pause`), the ring is downgraded from destructive to gold — `highestSeverity(warnings)` is
never consulted. The messages remain visible in the list and tooltip, so this is presentation only,
but it weakens a legal-compliance signal that shipped before this diff.
*Fix:* take the maximum of both severities rather than short-circuiting.

### R9 — MINOR: customer order/delivery mails got new, incorrect footer copy

`app/api/email/process-outbox/route.ts:145`

The N5 fix edited the shared `emailShell` footer for **all** templates:
“Diese E-Mail bekommst du weil du bei uns bestellt hast — keine Werbung.” →
“Diese E-Mail gehört zu deinem Betrieb — keine Werbung.” `order_confirmation`,
`delivery_unterwegs`, `delivery_delivered` and `delivery_abholbereit` go to guests, who have no

*Fix:* pass the footer sentence per template instead of changing the shared default.

### R10 — MINOR: the new schedule mails contain a non-functional link

`app/api/email/process-outbox/route.ts:152`

`<a href="/mitarbeiter">` is a root-relative URL inside an e-mail body; mail clients have no base URL,
so the link does not resolve. `renderByTemplate` already receives `ctx.origin`, which the delivery
templates use.
*Fix:* `href="${ctx.origin}/mitarbeiter"`.

### R11 — MINOR: template-slot audit entries are not tenant-attributable

`migration:222`; `schedule_template_slots` DDL at `:9-15`

`schedule_template_slots` is the only one of the five new tables without a `tenant_id` column, and
`unified_audit_change()` derives `audit_log.tenant_id` from `to_jsonb(new)->>'tenant_id'`.
*(empirically verified)*: after creating and editing a week template, all three
`entity_type='schedule_template_slots'` audit rows have `tenant_id IS NULL`, while
`schedule_templates` and `schedule_weeks` rows are attributed correctly. Any tenant-scoped audit view
will silently omit slot changes. `audit_log.tenant_id` is nullable, so nothing errors.
*Fix:* denormalise `tenant_id` onto `schedule_template_slots`, or audit slots via their parent.

### R12 — MINOR: the instance key omits `end_time` and slot name

`migration:120`

The key is `template_id:weekday:start_time:position:n:week_start`. Two slots in one template that
share weekday, start time and position but differ in end time (e.g. Mo 08:00–12:00 and Mo 08:00–16:00
“Aushilfe”) collapse onto the same key; the second is silently swallowed by `on conflict … do
nothing` and the route reports a lower “N offene Schichten erstellt” without saying anything was
skipped.
*Fix:* include `end_time` (and the slot name) in the key.

### R13 — MINOR: the deadline round-trip is Berlin on read but browser-local on write

`app/(admin)/schedule/planning-controls.tsx:11` vs. `:15`

The value is now rendered in `Europe/Berlin` (correct, N2), but submitted via
`new Date(deadline).toISOString()`, which parses the `datetime-local` string in the **browser's**
zone. For a Berlin browser the round-trip is stable; for any other zone the displayed value and the
stored value now diverge by the offset in both directions.
*Fix:* convert the Berlin wall-clock string to an instant explicitly rather than via `new Date`.

### T1 (round 0 NOTE) → MAJOR: the DB regression test for lock ordering now fails

## Summary

The fix round is substantial and honest: all 22 round-0 findings verify as genuinely fixed, the
migration is now idempotent and passes the dry-run against the production snapshot, the conflict
engine is wired into both the board and the assistant, and the availability loop reaches candidate
selection. The three gates are green.

What blocks approval is that two of the repairs reach further than intended and one pre-existing
defect went unnoticed by both of us in round 0. Publishing a schedule and editing any shift in a
published week both abort on an invalid `notification_type` enum value (R1, R2) — the second of which
breaks the already-shipped week board, not just this packet. And the B3 repair, by re-implementing
candidate selection beside `_core` rather than inside it, silently dropped that engine's
double-booking guard and its recurring-availability filter (R4, R5), which I confirmed by running
both engines side by side on seeded data. None of these are visible to vitest, `tsc` or a DDL-only
dry-run, which is why the green gates should not be read as coverage here.

Blockers remain, so this packet is still not approved.
