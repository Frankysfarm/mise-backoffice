## BLOCKER

**BLOCKER-1 — Migration bricht bei Legacy-Schritten ab, die reine Strings sind**
`supabase/migrations/20260831150000_visual_shift_guide_editor.sql:59`
Verifiziert, nicht vermutet: mit einem Leitfaden der Form
`{"categories":[{"name":"Check","steps":["Kasse zaehlen","Toilette pruefen"]}]}`
bricht die Migration mit `ERROR: cannot delete from scalar` ab und rollt die
komplette Transaktion zurück — inklusive Spalten, Index, RLS und Policies. Der
Ausdruck `(s.value - array[...])` setzt ein jsonb-Objekt voraus.
Dass dieser Fall real erwartet wird, zeigt `lib/ablaeufe/schema.ts:52`, wo der
TS-Normalizer String-Schritte ausdrücklich als `{ title: step }` abfängt — die
SQL-Variante tut das nicht. Der Report bestätigt, dass die Migration nie gegen
eine DB lief; genau dieser Pfad ist damit ungetestet in die Deploy-Kette gegangen.
*Fix:* `case when jsonb_typeof(s.value)='object' then s.value - array[...] else '{}'::jsonb end`
verwenden und `s.value->>'title'` für Skalare auf `s.value #>> '{}'` zurückfallen lassen.

**BLOCKER-2 — Editor löscht beim Speichern still alle Kategorien außer der ersten**
`app/(admin)/shift-guides/[id]/editor.tsx:19-20`
`const steps = form.content.categories[0]?.steps ?? []` und
`categories: [{ ...current.content.categories[0], steps: next }]` reduzieren den
Inhalt auf ein einziges Kategorien-Objekt. Sobald der Owner einen Schritt
hinzufügt, löscht, ändert oder sortiert, wird beim Speichern der gesamte Rest
des Ablaufs überschrieben. Der kanonische Speicher ist laut Audit
`inhalt.categories[].steps[]` (Mehrzahl); mein Fixture „Barista – Öffnung" mit
den Kategorien Vorbereitung/Maschine/Abschluss überlebt die Migration korrekt mit
`cats = 3` und würde beim ersten Editor-Speichern auf 1 Kategorie mit 2 Schritten
zusammenfallen. Datenverlust ohne Warnung, ohne Undo; die Versionszählung
(`version+1`) verdeckt ihn zusätzlich. Kategorien ab der zweiten sind im Editor
außerdem überhaupt nicht sichtbar, der Owner sieht den Verlust also nicht kommen.
*Fix:* alle Kategorien rendern und beim Patchen nur die betroffene Kategorie
ersetzen (`categories.map((c,i) => i===catIndex ? {...c, steps:next} : c)`).

### BLOCKER

**NEW-BLOCKER-1 — Migration ist gegen das Produktionsschema nicht anwendbar**
`supabase/migrations/20260831150000_visual_shift_guide_editor.sql:19,24`
Der Dry-Run gegen den Prod-Schema-Snapshot (`supabase/postgres:15.8.1.085`)
bricht sofort ab: `ERROR: function min(uuid) does not exist`. Die
`min()`/`max()`-Aggregate für `uuid` existieren in dieser PostgreSQL-Version
nicht. Da alles in einer Transaktion liegt, wird **nichts** angewendet — weder
Spalten noch Index, RLS, Policies oder Normalisierung. Der MAJOR-1-Fix hat
diesen Fehler eingeführt (die Runde-0-Fassung enthielt keine Aggregate).
*Fix:* `(array_agg(id))[1]` oder `(select id from public.tenants order by id limit 1)`
mit separatem `count(*)=1`-Guard. Mit dieser Ersetzung läuft die Migration
sauber durch (`OK patched-mig.sql`) — der Rest ist in Ordnung.

**NEW-BLOCKER-2 — Jeder Ablauf außer „Öffnung"/„Schließung" lässt sich nicht speichern**
`app/api/ablaeufe/guides/[id]/route.ts:35`, `app/api/ablaeufe/checkups/[id]/route.ts:9,38`

```
update public.shift_guides set phase='middle', ablauf_typ='cleaning' where id=…;
ERROR:  invalid input value for enum shift_guide_phase: "middle"
```
Der Owner bekommt „Ablauf konnte nicht gespeichert werden." (500) und verliert
seine gesamte Editor-Eingabe. Dieselbe Route-Konstante trifft

*Fix:* `midday` statt `middle` schreiben (und den Zod-Enum der Checkup-Route

**NEW-BLOCKER-3 — Gespeicherte Kontrolllisten werden für Sessions und HACCP-PDF leer**

### MAJOR

**NEW-MAJOR-1 — Legacy-Feldwerte lassen die Migration weiterhin komplett scheitern**
`supabase/migrations/20260831150000_visual_shift_guide_editor.sql:73`
`coalesce(nullif(s.value->>'required','')::boolean, nullif(s.value->>'pflicht','')::boolean, true)`
castet ungeprüft. Real nachgestellt: ein einziger Schritt
`{"title":"A","required":"ja"}` bricht die Normalisierung und damit die gesamte
Transaktion ab:
```
ERROR:  invalid input syntax for type boolean: "ja"
```
Das ist derselbe Fehlermodus wie BLOCKER-1, nur für Werte statt Typen; der Fix
hat ihn nur für skalare Schritte geschlossen. `"1"`/`"true"` casten, `"ja"`,
`"nein"`, `"yes"` nicht — bei einem deutschsprachigen Legacy-Feld `pflicht` ist
das nicht exotisch. Da der Snapshot schema-only ist, kann ich nicht
verifizieren, ob solche Zeilen in Produktion existieren; die Migration hat aber
keine Absicherung.
*Fix:* `case when s.value->>'required' in ('true','t','1','ja','yes') then true
when s.value->>'required' in ('false','f','0','nein','no') then false else … end`
statt eines direkten Casts.

**NEW-MAJOR-2 — Manager speichern Kontrolllisten ins Leere, bekommen aber „gespeichert"**
`app/api/ablaeufe/checkups/[id]/route.ts:22,26,36-47`
Die Route lässt `manager` ausdrücklich zu (`:22`), schreibt aber mit dem
Benutzer-Client (`createClient()`), und die einzige Write-Policy im
Produktionsschema ist
`checkup_templates_write_bo … ALL using is_backoffice() with check is_backoffice()`
mit `is_backoffice() = has_role(['backoffice','admin'])`. Ein Manager-Update
trifft damit 0 Zeilen, PostgREST meldet **keinen** Fehler, die Route antwortet
200 und die UI zeigt „Kontrolliste wurde gespeichert." Der Owner glaubt, seine
Kontrollschritte seien gesichert; sie sind es nicht.
*Fix:* entweder die Policy auf Standort-Manager ausweiten oder in der Route die
betroffene Zeilenzahl prüfen (`.select()` + leeres Ergebnis → 403) und `manager`
aus der Rollenliste entfernen, solange die Policy es nicht erlaubt.

**NEW-MAJOR-3 — Kontrolllisten sind über die neue Route mandantenübergreifend überschreibbar**
`app/api/ablaeufe/checkups/[id]/route.ts:27-34`
`checkup_templates` hat im Produktionsschema **kein** `tenant_id`, die
Read-Policy ist `checkup_templates_read_all … using (uid() is not null)`, und die
Route lädt `existing` allein über die ID ohne jede Scope-Bedingung. Wird
`departmentId` als `null` gesendet, findet überhaupt keine Prüfung statt.
Ein `backoffice`/`admin` aus Tenant A kann damit die Kontrollliste von Tenant B
per POST auf deren ID vollständig überschreiben (Titel, Bereich, Intervall,
Eskalation, Inhalt). Der Rest des Repos scopet solche Writes explizit
(`app/api/ablaeufe/guides/[id]/route.ts:23,27`). Die Lücke existierte in
Ansätzen schon im alten Client-Editor, wird durch die neue serverseitige Route
aber als „rollen- und RLS-gebunden" ausgewiesen, ohne es zu sein.
*Fix:* `checkup_templates` über `location_id` (bzw. eine ergänzte `tenant_id`)
gegen den Actor-Tenant auflösen, bevor geschrieben wird.
