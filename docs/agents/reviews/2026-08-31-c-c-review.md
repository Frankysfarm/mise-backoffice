## BLOCKER

### B1 — `materialize_recurring_operational_tasks` has no tenant/location scope and is reachable from a user route
`supabase/migrations/20260831120000_recurring_tasks_and_handover_ack.sql:124` (called from `app/api/operations/tasks/route.ts:47`)

The cursor is `select * from public.operational_task_templates where trigger_type='manual' and aktiv and paused_at is null and deleted_at is null` — no `tenant_id`/`location_id` predicate, and the function accepts no tenant argument. The API route validates the caller's location (`route.ts:25-29`) and then discards `input.locationId` entirely. Failure mode: a manager of tenant A pressing „Jetzt erzeugen" writes `operational_tasks` rows into **every other tenant and location in the database**, and the returned count reflects foreign tenants' data. This is the exact scope violation coordination rule 1 forbids.
*Fix:* add `p_tenant_id uuid, p_location_id uuid` parameters, filter the template cursor on both, and pass the already-validated `actor.tenant_id` / `input.locationId` from the route (the cron path may loop per tenant).

### B2 — „Individueller Rhythmus" materializes daily; the owner-facing preview disagrees with the database
`supabase/migrations/20260831120000_recurring_tasks_and_handover_ack.sql:105,112` vs `lib/operations/recurrence.ts:63`

`v_anchor := coalesce((p_rule->>'anchor')::date, p_day)`. The client never puts `anchor` into `recurrence_rule` (`operations-client.tsx:16` builds `{kind,time,weekdays,day,ordinal,weekday,interval,unit}`), and `save_recurring_operational_template` stores the rule verbatim (`migration:88`) — it writes the anchor only into the unused `recurrence_anchor` **column**, which `recurring_template_due_at` never reads. So `v_anchor = p_day` and `(p_day - v_anchor) % N = 0` is **true on every day**. Failure mode: owner selects „alle 2 Tage", the preview correctly shows 31.08./02.09./04.09., and the materializer then creates the task on 31.08., 01.09., 02.09., … — 14 duplicate-looking tasks per fortnight instead of 7. The same fallback makes `weekly` degenerate to daily for any rule saved without `weekday`.
*Fix:* pass `v_template.recurrence_anchor` into `recurring_template_due_at` and use it as the interval origin (`(p_day - v_anchor::date) % N`), and unit-test the SQL, not only the TypeScript twin.

### B3 — Two incompatible handover acknowledgement paths on the same table; the legacy path destroys the audit chain
`supabase/migrations/20260831120000_...sql:152-156` vs `app/api/operations/responsibility/route.ts:336-337`, list filters at `app/mitarbeiter/page.tsx:153` and `app/(neo)/neo/app/mitarbeiter/page.tsx:63`

The pre-existing „Übergabe annehmen" button (`app/mitarbeiter/my-operations.tsx:73`, `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:323`) still writes `status='angenommen', accepted_at, accepted_by` directly, skipping `read_at`/`confirmed_at`. Failure mode A: a handover created in the new UI and accepted in the Mitarbeiter-App shows forever as **„Ungelesen"** with an amber unconfirmed border in the new Übergabe-Audit, and the packet's required chain (wer gelesen, wer bestätigt, wann) is permanently empty for it. Failure mode B: the reverse — the new „Gelesen" action sets `status='gelesen'`, which is **not** in the `.in('status',['offen','angenommen'])` filters of either Mitarbeiter view, so the handover silently disappears from the recipient's app, and the legacy `accept_handover` (`.eq('status','offen')`, `route.ts:337`) then returns 409 „Übergabe wurde bereits bearbeitet." This violates coordination rule 5 (no parallel systems) as well as owner point 4.
*Fix:* route the legacy `accept_handover` through `acknowledge_responsibility_handover` (read+confirm in one call) and add `'gelesen'` to both Mitarbeiter status filters.

### B4 — The incoming shift cannot acknowledge a handover: the only UI is manager-plus
`app/(neo)/neo/app/ablaeufe/aufgaben/page.tsx:9`

`requireManagerPlus()` allows only `manager|backoffice|admin` (`lib/auth/requireRole.ts:15-17`); `teamleiter`, `mitarbeiter` and all service roles are redirected to `/login?reason=forbidden`. The new „Gelesen"/„Bestätigt" buttons (`operations-client.tsx:27`) exist nowhere else, and nothing was added to `app/mitarbeiter/*`. Failure mode: the Folgeschicht — the persona the owner explicitly names in point 4 and the report's own „Mobile — Folgeschicht/Mitarbeiter" click path — literally cannot open the page it is told to open, so „Gelesen + Bestätigt mit Person und Zeitstempel" is unreachable in production. The API allows these roles; only the UI gate blocks them.
*Fix:* surface the read/confirm buttons in the existing `app/mitarbeiter` handover card (which already renders for the recipient) rather than only behind `requireManagerPlus`.

## MAJOR

### M1 — New `create_handover` endpoint bypasses the existing role gate on the same table
`app/api/operations/tasks/route.ts:51-54`

The pre-existing writer requires manager **or** department lead (`app/api/operations/responsibility/route.ts:317-318`). The new action performs no role check at all, so any authenticated employee — `mitarbeiter`, `server`, `cook`, kiosk accounts — can insert a binding handover record naming an arbitrary colleague as recipient. Since no non-manager UI exists (see B4), the loosened check buys nothing and only removes a deliberate control.
*Fix:* apply the same `manager || isDepartmentLead(actor, departmentId)` check before the insert.

### M2 — „Pausieren" and „Löschen" leave up to 14 days of already-materialized instances
`app/api/operations/tasks/route.ts:40` and `supabase/migrations/20260831120000_...sql:119`

The materializer runs on a 14-day horizon every 3 minutes (`vercel.json:8-11`), so at any moment ~14 days of future instances exist. Pause/delete only flips `aktiv`/`paused_at`/`deleted_at` on the template and never touches `operational_tasks`. Failure mode: the owner pauses „Kaffeemaschine reinigen", and the task keeps appearing, escalating and e-mailing staff daily for two weeks — the control looks broken.
*Fix:* on pause/delete also cancel future instances (`update operational_tasks set status='storniert' where template_id=… and recurrence_due_at > now() and status='offen'`).

### M3 — Weekday numbers are rendered raw in the owner UI
`lib/operations/recurrence.ts:71,74`

`recurrenceLabel` returns `Wochentage: 1, 3, 5` and `Monatlich: 1. Wochentag`. These ISO-weekday integers are shown as the headline badge of every rule card (`operations-client.tsx:25`). Owner point 7 forbids technical data in the normal UI, and „1. Wochentag" is not meaningful German.
*Fix:* map to `['Mo','Di','Mi','Do','Fr','Sa','So']` and render „Jeden 1. Montag im Monat".

### M4 — Weekly and monthly-weekday recurrences are hard-wired to Monday
`app/(neo)/neo/app/ablaeufe/aufgaben/operations-client.tsx:24` (conditional fields), `:12` (`weekday:1, ordinal:1`)

The form renders extra inputs only for `weekdays`, `monthly_day` and `interval`. Choosing „Wöchentlich" or „Monatlich · erster Montag" leaves `weekday`/`ordinal` at their defaults, so every such rule fires on Monday / the first Monday, with no way to pick another day and no indication in the label.
*Fix:* show the weekday chooser for `weekly` and a weekday+ordinal pair for `monthly_weekday`.

### M5 — Übergabe-Audit has no date-range filter; the owner is told to edit the URL
`app/(neo)/neo/app/ablaeufe/aufgaben/operations-client.tsx:27`

The copy reads „Standort und Zeitraum lassen sich über die Seitenadresse filtern." The page reads `from`/`to` from `searchParams` (`page.tsx:18-19`) but renders no date inputs. The packet requires „Filter by Standort and date range"; asking an owner to hand-edit query strings is exactly the technical knowledge the owner order rules out.
*Fix:* add two `<input type="date">` fields that push `?from=…&to=…`.

### M6 — Handover „offene Aufgaben" are captured but never shown to the incoming shift
`app/(neo)/neo/app/ablaeufe/aufgaben/operations-client.tsx:26` (write) vs `:27` (audit render)

`open_task_ids` is collected (all open tasks preselected) and stored, but the audit card renders only `incidents`, `inventory_notes`, `damage_notes`, `cleaning_notes`, `important_notes`. Failure mode: the Folgeschicht confirms a handover without ever seeing the open tasks it is confirming — the first bullet of owner point 4 produces write-only data.
*Fix:* join the task titles for `open_task_ids` in `page.tsx` and list them in the audit card.

### M7 — Raw database exception text is surfaced as the owner-facing error banner
`app/api/operations/tasks/route.ts:63` → `operations-client.tsx:17,21`

The catch-all returns `error.message` verbatim, and the client renders `result.error` in the red banner. Failure mode: two managers edit concurrently and the second sees the red banner „template outside location"; a constraint violation shows `new row for relation "operational_task_templates" violates check constraint …`. English/technical strings in a German owner UI.
*Fix:* log the raw message server-side and return a fixed German sentence (the sibling helper at `app/api/operations/responsibility/route.ts:352-357` sanitises only a few patterns and is not a sufficient model).

### M8 — Every escalation e-mails each recipient twice
`app/api/cron/operational-escalations/route.ts:38,41`

The lookback is `now - 5 min` while the cron fires every 3 minutes (`vercel.json:10`), so a task whose `last_escalated_at` was just set matches on the current run **and** the next one. With three escalation levels that is six e-mails per overdue task, with no outbox/dedupe row.
*Fix:* make the window match the cadence (or persist a `escalation_email_sent_at` marker and filter on it).

### M9 — The ack-state-machine unit test exercises dead code, not the shipped behaviour
`lib/operations/handover-state.ts:3`, `tests/operations/recurring-tasks-handovers.test.ts:24-30`

`advanceHandover` is imported by the test only — no route, page or component uses it. Production acknowledgement lives in `acknowledge_responsibility_handover` (`migration:144`), which behaves **differently**: the TS twin treats a repeated „read" as idempotent (`readAt: state.readAt ?? at`), the SQL falls through to `raise exception 'invalid handover action'`. The packet asked for tests of the ack state machine; the green test provides no evidence about what actually ships.
*Fix:* delete `handover-state.ts` and cover the RPC in `scripts/tests/077_…sql`, or make the route call the TS machine.
