## BLOCKER

### B1 — `materialize_recurring_operational_tasks` has no tenant/location scope and is reachable from a user route
`supabase/migrations/20260831120000_recurring_tasks_and_handover_ack.sql:124` (called from `app/api/operations/tasks/route.ts:47`)

The cursor is `select * from public.operational_task_templates where trigger_type='manual' and aktiv and paused_at is null and deleted_at is null` — no `tenant_id`/`location_id` predicate, and the function accepts no tenant argument. The API route validates the caller's location (`route.ts:25-29`) and then discards `input.locationId` entirely. Failure mode: a manager of tenant A pressing „Jetzt erzeugen" writes `operational_tasks` rows into **every other tenant and location in the database**, and the returned count reflects foreign tenants' data. This is the exact scope violation coordination rule 1 forbids.
*Fix:* add `p_tenant_id uuid, p_location_id uuid` parameters, filter the template cursor on both, and pass the already-validated `actor.tenant_id` / `input.locationId` from the route (the cron path may loop per tenant).

### B2 — „Individueller Rhythmus" materializes daily; the owner-facing preview disagrees with the database
`supabase/migrations/20260831120000_recurring_tasks_and_handover_ack.sql:105,112` vs `lib/operations/recurrence.ts:63`

`v_anchor := coalesce((p_rule->>'anchor')::date, p_day)`. The client never puts `anchor` into `recurrence_rule` (`operations-client.tsx:16` builds `{kind,time,weekdays,day,ordinal,weekday,interval,unit}`), and `save_recurring_operational_template` stores the rule verbatim (`migration:88`) — it writes the anchor only into the unused `recurrence_anchor` **column**, which `recurring_template_due_at` never reads. So `v_anchor = p_day` and `(p_day - v_anchor) % N = 0` is **true on every day**. Failure mode: owner selects „alle 2 Tage", the preview correctly shows 31.08./02.09./04.09., and the materializer then creates the task on 31.08., 01.09., 02.09., … — 14 duplicate-looking tasks per fortnight instead of 7. The same fallback makes `weekly` degenerate to daily for any rule saved without `weekday`.
*Fix:* pass `v_template.recurrence_anchor` into `recurring_template_due_at` and use it as the interval origin (`(p_day - v_anchor::date) % N`), and unit-test the SQL, not only the TypeScript twin.

### B3 — Two incompatible handover acknowledgement paths on the same table; the legacy path destroys the audit chain
`supabase/migrations/20260831120000_...sql:152-156` vs `app/api/operations/responsibility/route.ts:336-337`, list filters at `app/mitarbeiter/page.tsx:153` and `app/(neo)/neo/app/mitarbeiter/page.tsx:63`

The pre-existing „Übergabe annehmen" button (`app/mitarbeiter/my-operations.tsx:73`, `app/(neo)/neo/app/mitarbeiter/responsibility-client.tsx:323`) still writes `status='angenommen', accepted_at, accepted_by` directly, skipping `read_at`/`confirmed_at`. Failure mode A: a handover created in the new UI and accepted in the Mitarbeiter-App shows forever as **„Ungelesen"** with an amber unconfirmed border in the new Übergabe-Audit, and the packet's required chain (wer gelesen, wer bestätigt, wann) is permanently empty for it. Failure mode B: the reverse — the new „Gelesen" action sets `status='gelesen'`, which is **not** in the `.in('status',['offen','angenommen'])` filters of either Mitarbeiter view, so the handover silently disappears from the recipient's app, and the legacy `accept_handover` (`.eq('status','offen')`, `route.ts:337`) then returns 409 „Übergabe wurde bereits bearbeitet." This violates coordination rule 5 (no parallel systems) as well as owner point 4.
*Fix:* route the legacy `accept_handover` through `acknowledge_responsibility_handover` (read+confirm in one call) and add `'gelesen'` to both Mitarbeiter status filters.

### B4 — The incoming shift cannot acknowledge a handover: the only UI is manager-plus
`app/(neo)/neo/app/ablaeufe/aufgaben/page.tsx:9`

`requireManagerPlus()` allows only `manager|backoffice|admin` (`lib/auth/requireRole.ts:15-17`); `teamleiter`, `mitarbeiter` and all service roles are redirected to `/login?reason=forbidden`. The new „Gelesen"/„Bestätigt" buttons (`operations-client.tsx:27`) exist nowhere else, and nothing was added to `app/mitarbeiter/*`. Failure mode: the Folgeschicht — the persona the owner explicitly names in point 4 and the report's own „Mobile — Folgeschicht/Mitarbeiter" click path — literally cannot open the page it is told to open, so „Gelesen + Bestätigt mit Person und Zeitstempel" is unreachable in production. The API allows these roles; only the UI gate blocks them.
*Fix:* surface the read/confirm buttons in the existing `app/mitarbeiter` handover card (which already renders for the recipient) rather than only behind `requireManagerPlus`.

### M8 — Every escalation e-mails each recipient twice
