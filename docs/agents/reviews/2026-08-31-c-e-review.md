## BLOCKER

**B1 — New "Lagerplan" tile 404s in the admin shell.**
`app/(admin)/inventory/page.tsx:50` — the tile is built from the shared `basePath` returned by `operationsBasePath('/inventory', '/neo/app/lager')` (`lib/routing/operations-base-path.ts`), but only `app/(neo)/neo/app/lager/plan/` was created; there is no `app/(admin)/inventory/plan/`. **B2 — The migration's hierarchy trigger breaks the still-reachable legacy shelf editor.**
`supabase/migrations/20260831140000_inventory_warehouse_plan.sql:32` (+ trigger at `:42`) raises `inventory place requires a unit` for any `place_kind='place'` row without a parent. `place_kind` defaults to `'place'` (`:4`), and `app/(admin)/inventory/shelves/editor.tsx:29` — reachable at `/inventory/shelves`, still linked from `app/(admin)/inventory/page.tsx:51` — inserts `inventory_shelves` rows with neither `parent_shelf_id` nor `place_kind`. After this migration every "Fach anlegen" in that editor fails with a raw English database exception. Existing functionality is regressed with no migration of the caller.
*Fix:* treat a parentless row as a `unit` in the trigger (or allow parentless places), or update the legacy editor to pass `place_kind`/`parent_shelf_id`.

**B3 — Movement `typ` vocabulary diverges from the canonical one.**
`supabase/migrations/20260831140000_inventory_warehouse_plan.sql:83,84,87` writes `'zugang'`, `'entnahme'` and `'umlagerung'`. The canonical vocabulary rendered by the Bewegungen audit trail is `eingang | ausgang | inventur | schwund | korrektur | transfer | verbrauch` (`app/(admin)/inventory/movements/page.tsx:11-19`), and `scripts/migrations/073_inventory_tenant_integrity.sql` uses `'inventur'`. Consequence: `TYP_LABELS[m.typ] ?? { label: m.typ }` (`movements/page.tsx:49`) falls through and prints the raw technical string as the badge; and if `stock_movements.typ` carries a CHECK constraint over the existing vocabulary (the base DDL is not in this repo, so it could not be confirmed here), **every** Einbuchen/Entnehmen/Umlagern/Zählen from the QR page fails at runtime.
*Fix:* use `eingang` / `ausgang` / `transfer` / `inventur`.

**B4 — The count action re-introduces the parallel stock-write path that migration 074 removed.**
`supabase/migrations/20260831140000_inventory_warehouse_plan.sql:73,80,87` — for `p_action='count'` the RPC updates `inventory_items.letzte_inventur` and inserts into `stock_movements` directly. `scripts/migrations/074_inventory_count_single_movement.sql` exists precisely to make `inventory_counts` (via `trg_inventory_count_movement`) the single owner of that pair, and `tests/inventory/inventory-integrity.test.ts:30-31` encodes the invariant. The scan count therefore never reaches `inventory_counts`, so the Inventuren/Abweichungen screens for management show nothing — the packet's "deviations are listed for management" acceptance criterion is unmet — and two competing count paths now exist (coordination rule 5, "no parallel systems"). The integrity test still passes only because it asserts against the *074 file*, not against new migrations.
*Fix:* have the count action insert into `inventory_counts` and let the canonical trigger own the movement and the stock update.

## NEW findings

**N1 — BLOCKER — "Einbuchen" and "Entnehmen" fail on every call: `movement_type` enum vs. `text`.**
`supabase/migrations/20260831140000_inventory_warehouse_plan.sql:104-105` inserts
`case p_action when 'book' then 'eingang' else 'ausgang' end` into `stock_movements.typ`.
In the production snapshot `stock_movements.typ` is **not** `text` — it is the enum `movement_type` (labels `eingang, ausgang, inventur, schwund, korrektur, transfer, verbrauch`). PostgreSQL resolves the `CASE` result type to `text` and refuses the implicit assignment cast.
*Observed against the snapshot, both actions:*
```
ERROR:  column "typ" is of type movement_type but expression is of type text
CONTEXT: PL/pgSQL function record_inventory_place_action_as_actor(...) line 31
```
`transfer` and `count` are unaffected — they pass a bare literal / go through the count trigger — which is why this is invisible without executing the RPC. Consequence: the two primary mobile scan actions never work; the API maps the failure to the generic "Die Änderung konnte nicht gespeichert werden." toast, so staff get no usable signal. This is a regression introduced by the B3 fix: the pre-fix code inserted the literal `'zugang'` directly, which would have failed differently but for the same underlying reason.
*Fix:* cast explicitly — `(case … end)::public.movement_type` — or split into two `if` branches with bare literals as the `transfer`/`inventur` paths already do.

**N2 — MAJOR — auto-reorder now writes the same product into two order drafts and mislabels the supplier.**
`app/api/inventory/auto-reorder/route.ts:44-58` rebuilds each group by re-filtering `underMin`:
`item.supplier_id ? item.supplier_id === proposal.supplierId : (item.lieferant ?? "Ohne Lieferant") === proposal.supplierName`.
`groupReorderProposals` sets `supplierName = lieferant ?? "Ohne Lieferant"` (`lib/inventory/warehouse-plan.ts:97`), so a group keyed on a real `supplier_id` whose item has `lieferant = null` carries `supplierName = "Ohne Lieferant"` — and every supplier-less item in the same location then matches its `else` branch.
*Reproduced:* item A (`supplier_id = aaaa…0001`, `lieferant = null`) and item B (`supplier_id = null`, `lieferant = null`), both under minimum in location `loc1`, produce
`loc1:aaaa…0001 → items: Milch, Zucker` and `loc1:Ohne Lieferant → items: Zucker`.
"Zucker" is ordered twice, in two separate `order_lists` drafts, and the supplier-linked draft is labelled `Ohne Lieferant` instead of the supplier. The pre-fix code grouped each item exactly once. This is money leaving the business twice.
*Fix:* carry the item list out of `groupReorderProposals` (or key the re-filter on the same composite key the grouper used) instead of re-deriving membership from a lossy display name.

**N3 — MAJOR — deleting a Lagerplatz silently detaches its products, while the UI claims products prevent deletion.**
`inventory_items_shelf_id_fkey` is `ON DELETE SET NULL` in the production schema, so `delete_inventory_place_as_actor` (`…140000….sql:59-66`) hits no `foreign_key_violation` for a place that still holds stock.
*Observed:* deleted a place holding "Mehl" (7 kg recorded) → RPC returned successfully, `inventory_items.shelf_id` became `NULL`, the product silently lost its location.
