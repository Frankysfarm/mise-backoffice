# Packet C-D — Dienstplan Vollausbau

## AUDIT

### Existed

- `/neo/app/dienstplan` reused the established `shifts` week board, manual creation/editing, drag-and-drop, PDF, swap requests and ArbZG validation.
- `/neo/app/dienstplan/templates` exposed CRUD for individual `shift_templates` (name, time, position, break, type, department, location), but not a complete week template with weekday/headcount.
- `employee_availability` and `availability_exceptions` already represented recurring availability, preferred periods, vacation and sickness.
- `weekly_shift_assignment_suggestions`, `generate_weekly_shift_assignment_suggestions` and `confirm_weekly_shift_assignment_suggestion` already provided a deterministic, explainable assistant. It considered regular/exception availability, department/responsibility fit, overlap and assigned weekly hours, and never assigned silently.
- `/mitarbeiter` already displayed the employee's assigned shifts.
- `notifications`, `email_outbox` and `/api/email/process-outbox` were the existing in-app/e-mail delivery mechanism.

### Hidden or unclear

- Individual shift templates were reachable through “Vorlagen”, but their relationship to a complete planning week was unclear.
- The weekly assistant existed, but had no explicit availability deadline, planning-round status or publish boundary.
- ArbZG warnings existed on the board, while qualification, absence and contract-hour conflicts did not share one structured conflict result.

### Missing

- Complete week-template CRUD/copy/delete, weekday/time-window headcount and idempotent application.
- Planning deadline, reminder action, employee states “kann / möchte / kann nicht” and concrete-shift application.
- Explicit draft → published workflow, publication/change records and affected-person notifications.
- A pure conflict function covering every packet-mandated conflict kind.

## CHANGES

- `app/(admin)/schedule/page.tsx`, `planning-controls.tsx`: planning-round controls for template application, deadline, reminders and publication.
- `app/(admin)/schedule/templates/page.tsx`, `week-template-manager.tsx`: owner-friendly complete week-template editor with multiple demand windows, copy and delete; existing individual shift blocks remain available.
- `app/api/scheduling/planner/route.ts`: authenticated manager/employee orchestration with tenant/location checks and service-role RPC calls.
- `app/mitarbeiter/page.tsx`, `availability-loop.tsx`: mobile-first open-shift view and the three availability/application states.
- `lib/scheduling/planner.ts`: pure idempotency, availability normalization, proposal scoring, structured conflict detection and affected-employee calculation.
- `tests/scheduling/*.test.ts`: 15 unit/contract cases.
- `tests/e2e/dienstplan-planning-loop.spec.ts`: authenticated desktop/mobile Playwright path, ready for a test backend/auth state.
- `supabase/migrations/20260831130000_schedule_planning_loop.sql`: additive data model and protected workflows.

## DB CHANGES

- New tables: `schedule_templates`, `schedule_template_slots`, `schedule_weeks`, `shift_availability_responses`, `schedule_publication_changes`.
- New `shifts.schedule_template_instance_key` plus a tenant/location unique partial index for idempotent application.
- RPCs: `manage_schedule_template`, `apply_schedule_template`, `publish_schedule_week` (service-role only).
- The existing `generate_weekly_shift_assignment_suggestions` is preserved as `_v1` and wrapped, not duplicated: the wrapper enforces the deadline and incorporates concrete “kann / möchte / kann nicht” responses.
- Trigger `shifts_published_schedule_change` records post-publication assignment/time/status changes and notifies only old/new affected employees.
- RLS: service-role write policies; authenticated manager reads use `current_tenant_id()` plus `can_manage_operational_location`; employee reads use tenant plus `current_employee_id()`/location access.
- E-mail is honestly queued through the existing `email_outbox`; actual sending remains the existing configured outbox processor/tenant Resend setup.
- Rollback: drop the new trigger/function/RPCs/tables and partial index, restore the `_v1` suggestion function name, then drop `shifts.schedule_template_instance_key`. Existing shifts and legacy `shift_templates` remain intact.

## HOW TO VERIFY MANUALLY

### Desktop owner

1. Open `Neo → Dienstplan → Vorlagen`.
2. Create a Wochenvorlage, add several weekdays/time windows, select area/position, pause and required people; save, edit, copy and delete it.
3. Return to `Neo → Dienstplan`, select one location/week/template, set the deadline and click “Vorlage anwenden”. Repeat once and verify the message says no duplicates were created.
4. Click “Verfügbarkeit anfragen”; verify employee notification and `email_outbox` row.
5. After the deadline click “Vorschläge berechnen”; inspect German reasons/open shifts, confirm or manually edit, then click “Dienstplan veröffentlichen”.
6. Change an assigned published shift and verify `schedule_publication_changes` plus notifications only for the old/new affected employees.

### Mobile employee

1. Open `/mitarbeiter`, choose “Verfügbarkeit”.
2. For offered shifts select “Kann”, “Möchte” (concrete application) or “Kann nicht”; reload and verify the state persists.
3. After publication open “Dienstplan” and verify only the employee's binding shifts are shown.
4. After an owner change, verify the “Dienstplan geändert” notification and the updated shift.
